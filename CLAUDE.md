# DJ Claude

This folder is a DJ rig that **you** (Claude) play. The user directs the set by typing here in Claude Code. The browser tab at http://localhost:4747 is just the sound system and visuals.

- Any message that sounds like a DJ instruction ("play X", "harder", "kill the bass", "mix into something darker", "get me some trance") is live direction: load the **dj** skill and act on it immediately with `node dj.mjs …`.
- "Play a set" / "DJ for me" / "take over" means the **dj-set** skill (autopilot you can steer).
- Before any `dj mix`, the **dj-mix** skill has the transition craft. Downloading and searching music is **dj-crate**. Recording the decks and rendering a video of a set is **dj-video**. Mashups are **dj-mashup**, speech clips as vocals **dj-voice**, a produced album **dj-album**, and anything broken **dj-troubleshoot**.
- During a live set, keep every `dj wait` at 60 s or less, because the user's messages only reach you between tool calls. Check for new user text after each tool call. The user's latest words beat your plan. Keep chat replies to one line per event.

## Layout
- The code is in `apps/` (`server/`: the server and its `lib/`; `web/public/`: the page; `cli/`: the CLI) and `tools/` (`produce/`, `bench/`). What the rig keeps (`config.json`, `.dj/`, `library/`, `bin/`, `.venv/`, `starter/`) stays in the project folder. `apps/server/lib/paths.mjs` is the one file that knows this layout; code takes its paths from it.
- `apps/server/server.mjs`: HTTP server. Holds the library, relays commands to the browser engine, long-poll `wait`, crowd inbox, booth log. One page is the engine at a time (`POST /api/engine/claim`): a page that is still connected keeps it unless the claim says `force`, and the answer `{ held, playing }` is what the other page asks its user with ("Take over", `start()` in `apps/web/public/app.js`; a page opened with `?takeover`, as the Playwright tools do, forces at once; the desktop app's own start never does).
- `apps/desktop/`: the Electron app (`pnpm desktop`): `main.mjs` starts the server as a utility process of its own, or attaches to one already on the port, and opens the page with `?desktop`, which makes `apps/web/public/app.js` start the engine without a click. `splash.html` is the start-up window: a local file shown at once, told each step by `main.mjs` (`step` / `done` / `failed`: server, the `/api/health` checks, audio engine) while the DJ page loads hidden; the page is shown when the server hears from its engine. `window-state.mjs` puts the DJ window back where it was last closed (`.dj/desktop-window.json`: bounds and maximised; ignored when that place is no longer on a screen; no Electron in it, so `test/desktop-window.test.mjs` tests it in plain Node). `pnpm dist` builds the installer into `dist/` (`electron-builder.config.cjs`: the project folder is the app directory, laid out as in the repository, no asar, no node_modules); the `installer` job of `.github/workflows/release-please.yml` attaches it to each release. The installed app has no project folder, so `root.mjs` (imported first by `main.mjs`) points `DJ_ROOT` at Documents/DJ Claude and `rig-folder.mjs` makes that folder a whole project from what the app ships: the code, `dj.mjs`, `CLAUDE.md`, `tools/produce`, the skills and `starter/` (the app's own: replaced when the build changes, `.dj/app-build`; its `CLAUDE.md` is this file up to "## Layout" followed by `apps/desktop/CLAUDE.installed.md`, which describes that folder instead of the source tree, so what is above "## Layout" here must make sense to a player without the repository), and `config.json` and `.claude/settings.json` (the user's: copied once). Claude Code is opened in that folder. Anything a skill needs at run time must therefore be in the `files` list of `electron-builder.config.cjs`. The only part with npm dependencies (a pnpm workspace package). No background throttling; navigation is limited to the local server.
- `apps/drums/`: Claude-808, a drum machine, a separate project that lives here for now (it will move to its own repository): it imports nothing from the DJ code and the DJ code nothing from it. Its own server (`node apps/drums/server.mjs`, port 4748), page, CLI (`node apps/drums/cl808.mjs help`) and tests (`apps/drums/test/`, port 4868); see `apps/drums/README.md`. "Make me a beat" and anything about the drum machine is the **cl-808** skill.
- `apps/synth/`: MiniClaude, a polyphonic synthesizer, a separate project that lives here for now (it will move to its own repository): it imports nothing from the DJ code or the other apps and nothing imports it. Its own server (`node apps/synth/server.mjs`, port 4749), page, CLI (`node apps/synth/miniclaude.mjs help`) and tests (`apps/synth/test/`, port 4864); see `apps/synth/README.md`. A synth sound, a patch or a riff is the **miniclaude** skill.
- `apps/daw/`: Claudebase, a small DAW (drum and synth tracks, clips on a bar timeline), a separate project that lives here for now (it will move to its own repository): it imports nothing from the DJ code or the other apps and nothing imports it. Its own server (`node apps/daw/server.mjs`, port 4750), page, CLI (`node apps/daw/claudebase.mjs help`) and tests (`apps/daw/test/`, port 4866); see `apps/daw/README.md`. A song, an arrangement, a bass line or chords in the DAW is the **claudebase** skill.
- `apps/cli/dj.mjs`: CLI control surface. `dj.mjs` in the project folder is a shim for it, so `node dj.mjs help` works from there.
- `apps/server/lib/banner.mjs`: the server's startup banner. One of its `ANIMATIONS` plays at random (`DJ_BANNER=<name>` picks one), then the equaliser follows the live deck's beat (`banner.loop` setting, `DJ_BANNER_LOOP=0`). Plain text when the output is not a terminal. Preview them with `node dj.mjs banner [name]`.
- Health: `GET /api/health` (JSON, one ok/warn/fail/off entry per system: fail = a required system is down, warn = an optional one has a fault, built by `apps/server/lib/health.mjs`) and the page at `/health` (`apps/web/public/health.html`). Checks run only on request. The DJ page asks once a minute while visible: the status light in its header (`setStatus` / `refreshHealth` in `apps/web/public/ui/link.js`) turns amber on a warn, red on a fail, and links to `/health`.
- Visuals: the page at `/visuals` (`apps/web/public/visuals.html` + `apps/web/public/ui/visuals.js`), a full-screen WebGPU visualiser for a second screen; it only watches. The engine tab measures the master output (`apps/web/public/worklets/visuals-tap.js`, fed by `apps/web/public/ui/visuals-feed.js`, only while someone watches) and posts analysis frames; `apps/server/lib/visuals.mjs` (`VisualsHub`) fans them out on `GET /api/visuals/events` with the "scene" (key, energy, structure of what is on the decks) and relays the optional audio (`GET /api/visuals/audio`, a WebM stream the engine tab encodes only while someone listens; `visuals.audio` setting). With `visuals.lowLatency` on, the sound goes tab to tab over WebRTC instead and the hub only passes signalling (`POST /api/visuals/rtc` from a viewer, `/api/visuals/rtc/engine` from the engine tab, `visualsRtc` events to the engine); `visuals.maxListeners` caps it and the relay is the fallback. `apps/web/public/ui/visuals/sdp.js` makes the Opus line ask for stereo music. On the page: `apps/web/public/ui/visuals/feed.js` (frames → one smooth signal, colours from key and deck), `stage.js` (three.js `WebGPURenderer`, shared uniforms, crossfade between two render targets, device-loss recovery), `morph.js` (the shared GPU elements that modes with a `morph()` shape, so a change between two of them is a morph and not a crossfade; the quality tiers low / medium / high, `?quality=`), `audio.js` (the sound, and `Sync`, which keeps measuring where the sound is against the frames so the picture stays locked to it), `modes/*.js` (one module per mode; the interface is at the top of `stage.js` and, for modes that morph, of `morph.js`; the names are also in `MODES` in `apps/server/lib/visuals.mjs`). three.js is vendored in `apps/web/public/vendor/three/` (see its README). `dj visuals [<mode>|auto]` (`apps/cli/cli-ext/visuals.mjs`). Unrelated to the offline `tools/produce/viz.mjs`.
- Settings: the page at `/settings` (`apps/web/public/settings.html` + `apps/web/public/ui/settings.js`) edits config.json through `GET`/`POST /api/settings`; the page files the schema's groups under a few categories (`CATEGORIES` in `settings.js`), shows one at a time and has a search box. The schema, validation and which settings apply live vs after a restart are in `apps/server/lib/settings.mjs` (its `ui.*` settings reach the DJ page in the `hello` and `ui` server events, into `ui` in `apps/web/public/ui/state.js`); `applyLiveSettings()` in `apps/server/server.mjs` pushes the live ones into the running objects. Above the settings the page shows the project folder (`GET /api/folder`) with "Open folder" and "Open Claude Code here" (`POST /api/folder/open`, answered only to a page on the server's own machine; the commands per platform are in `apps/server/lib/reveal.mjs`).
- `apps/web/public/engine.js` + `apps/web/public/worklets/deck-player.js`: Web Audio engine. Four decks (C/D appear when loaded; A,C left / B,D right of the crossfader), key lock + key shift (WSOLA), per-stem playback (vocals/drums/bass/other), EQ/filter/echo, deck FX (reverb/flanger/phaser/gate/crush), 8-pad sampler, scratching, sample-accurate transitions. Engine CLI: `node dj.mjs help-engine`.
- `apps/web/public/app.js`: UI boot + per-frame render loop; the rest of the UI is ES modules in `apps/web/public/ui/` (`state.js` shared state, `link.js` server link + recorder, `commands.js` command handlers, `controls.js` knobs/buttons, `keys.js` chop keyboard + pads, `deck.js`, `layout.js` stacked/classic deck layout (`ui.deckLayout`) + the mixer's dB scale, `prefs.js` the `ui.*` settings on the page (localStorage copy, `saveUi`), `lower.js` the bottom panel: its tabs (Library, Sampler & keys, Booth: `ui.dockTab`, `ui.boothPinned`), hide and resize, `maximize.js` the panel maximised under a slim deck strip and the header's layout presets (Mix / Browse / Perform: `ui.layoutPreset`), `bindings.js` key bindings on the DJ page + the shortcut list (`settings-keys.js` is their editor on /settings; the actions are in `apps/server/lib/keymap.mjs`, served as `/keymap.mjs`, presets in `apps/server/lib/key-presets/`), `canvas.js` waveforms/jog wheels/meters, `turntable.js` the record player drawn in the jog wheel's place (`ui.deckStyle: turntable`: turning record, tonearm you can pick up to seek, hot cues as stickers), `hand.js` the scratch / nudge gestures shared by the jog wheel and the waveform, `wave.js` waveform gestures (drag to scratch, silent seek, nudge strip, zoom, double-click cue, the guard lock), `clock.js` the set timer and the time of day in the header (the start of the set is the server's: `apps/server/lib/set-clock.mjs`, in `hello` and the `set` event), `loader.js` loading a deck from the page + file import (`POST /api/upload`), `dragdrop.js` dragging rows and files onto decks (mouse and touch), `crate.js`, `booth.js`, `util.js`; `back.js` is for /health and /settings: their "Back to the decks" closes the tab or window while a DJ page is the engine, and loads the DJ page only when none is). `apps/web/public/index.html`. Styles are per component in `apps/web/public/css/` (load order in index.html matters). No build step.
- `apps/server/lib/analyze.mjs`: BPM/beat grid, key (Camelot), energy, structure. `apps/server/lib/library.mjs`: cache, search, suggestions. `apps/server/lib/downloader.mjs`: yt-dlp wrapper.
- `apps/server/lib/sequencer.mjs`: plan steps, track queue, auto-DJ (no AI: queue, then the active set, then the library). `apps/server/lib/sets.mjs`: saved sets, one JSON file each in `sets/` (the user's, beside `library/`), `dj sets` (`apps/cli/cli-ext/set.mjs`), `/api/sets`, the "Set" part of the page's "Up next" (`ui/crate.js`; library rows are dropped on it, `ui/dragdrop.js`); the active one and what of it has played is `.dj/active-set.json`. A set can keep the decks and the mixer (`snapshot`: `snapshotOf` / `restoreSteps` in `sets.mjs`, the `save` / `open` actions in `server.mjs`, "save decks" / "load decks" on the page); opening one replays engine commands quietly (`handleCmd({ quiet })`) and holds play tracking off meanwhile (`openingSet`). Automation: every change the engine makes goes through `Mixer._tap` (knobs via `Ctl.tap`, a deck's `_ev` transport events, key, crossfader side, FX, loads, hand scratching, the raw params in `Mixer.params()`, the sampler); `apps/web/public/automation-core.js` records those entries on the take's clock and replays them shifted onto another (no page dependencies: `test/automation.test.mjs` runs it on the Web Audio mock); `ui/automation.js` runs it for the active set (saves the decks as 0:00, opens the set to play, a worker as the clock) and the "Set" block has ● rec · ▶ play · ■ stop; `dj automation` (`apps/cli/cli-ext/set.mjs`) is the engine command `automation`; the take is `sets/<name>.automation.json` (`saveAutomation` in `sets.mjs`, `/api/sets/automation`); the sequencer waits while the engine reports `automation.mode` play or overdub. The Automation tab (`ui/lanes.js`, `css/lanes.css`, the `automation` tab in `ui/lower.js`) draws and edits a take's lanes (`ui/lane-model.js`: curves, handles, marks, edits; no page in it, `test/lanes.test.mjs`); the transport controls of both places are `ui/automation-ui.js` (with the active set and the questions). Export: `exportSet` in `ui/automation.js` records while it plays and asks `POST /api/export` (`exportSession` with `from` / `to` / `name`, which times a single recorder from the start it reports, `s` on each chunk) for `.dj/exports/<set>.mp3`, with the speakers off unless asked to listen (`Mixer.setSpeakers`: a gain between `out` and the sound card only; the recorder, meters and visuals tap `out`); "exports ↗" is `POST /api/folder/open { what: 'exports' }`. `apps/server/lib/monitor.mjs`: mix monitor + transition critiques. `apps/server/lib/memory.mjs` (.dj/memory.json), `apps/server/lib/cues.mjs` (.dj/cues.json), `apps/server/lib/sections.mjs`, `apps/server/lib/set-clock.mjs` (when a set starts and ends: 30 minutes without music), `apps/server/lib/music.mjs`, `apps/server/lib/fx.mjs`, `apps/server/lib/export.mjs`. Grid corrections: .dj/grid-edits.json.
- Tests: `node --test test/*.test.mjs test/server-*.mjs` (server tests run scratch copies on ports 4851-4858, 4861 and 4863 with a fake engine and a generated library, `test/fixtures.mjs`: synthetic tracks run through the real analyser, cached in the temp folder; they never read or touch the real library or .dj/). `test/desktop.test.mjs` starts the real desktop app (skipped when Electron is not installed) on a scratch project folder (`DJ_ROOT`) and a scratch Electron profile, ports 4859-4860 and 4862; `test/desktop-driver.mjs` is the part that runs inside Electron and reports what the windows do.
- CI: `.github/workflows/test.yml` runs the whole suite on Linux for every pull request and push to main (nothing when the change is only documentation, skills, pictures or the version files a release bumps: its `paths-ignore`; any other file, a comment in a code file included, runs it). `.github/workflows/desktop.yml` is the slow Windows part, the desktop start-up test with the real Electron: on a pull request only when its `paths` are touched (the desktop app, the server, the page, the CLI, the lockfile), plus the installer build on a push to main or when run by hand. A change to what the desktop app runs that lives elsewhere needs its path added there.
- Benchmarks: `node tools/bench/<name>.bench.mjs` (`analyze`, `deck-voice`, `zoom`, `library`) runs the working tree against the git ref in `tools/bench/baseline.json` (`BENCH_BASE=<ref>` overrides it) in one process and checks the output is byte-identical. Helpers in `tools/bench/util.mjs`.
- `.dj/library.json`: analysis cache. `.dj/server.log`: server log. `bin/`: auto-installed yt-dlp.
- Stems: `apps/server/lib/stems.mjs` + `apps/server/lib/separate.py` (htdemucs in the project `.venv`) split every track into `.dj/stems/<id>/` in the background; vocal maps via `node dj.mjs vocals <id>`. `node dj.mjs stems setup [--gpu]` (`apps/server/lib/stems-setup.mjs`, run by the CLI itself) installs the separator into `.venv` with uv; the queue finds a `.venv` made while the server runs.
- CLI extensions live in `apps/cli/cli-ext/*.mjs` (engine, stems, …).
- `starter/tracks.json`: Creative Commons starter crate; `node dj.mjs starter` (`apps/cli/cli-ext/starter.mjs`) or the "Download demo tracks" button on an empty crate (`POST /api/starter`) downloads it into `library/starter/`; both use `apps/server/lib/starter.mjs`. Credits and licences in `starter/README.md`.
- `tools/produce/`: video production. `record-browser.mjs` (Playwright page recording that becomes the sound system), `make-video.mjs` (set audio → 720p/480p video with visualiser + DJ-table footage), `viz.mjs`, `get-sample.mjs` / `measure-sample.mjs` (short samples into `.dj/produce/samples/`), `index-captions.mjs` + `find-line.mjs` + `analyze-speech.mjs` (speech index in `.dj/voice/`), `build-reel.mjs` + `remix.mjs`/`chops.mjs` (voice reels), `run-design.mjs` (live design runner, times in `.dj/produce/out/run-design-times.json`), `album-design.mjs` + `songs/README.md` (album plans from `.dj/produce/beds.mjs` + `.dj/produce/songs/`), `cut-track.mjs`, `full-album.mjs`, `align.mjs`.
- Docs for people: `README.md` is the short way in (what it is, quick start, an index); the detail is in `docs/` (`desktop-app.md`, `how-it-works.md`, `stems.md`, `visuals.md`, `production.md`, `configuration.md`, `development.md`). A change in behaviour that a person would notice goes into the matching page there, not into the README.
- Commits follow Conventional Commits (`feat(scope): …`, `fix(scope): …`, `refactor:`, `chore:`): release-please (`.github/workflows/release-please.yml`, `release-please-config.json`) builds the version and `CHANGELOG.md` from them, so the type decides the version bump (`feat` minor, `fix` patch) and the subject line is what the changelog shows.
- Needs Node 20+ and ffmpeg/ffprobe on PATH. No npm dependencies.
